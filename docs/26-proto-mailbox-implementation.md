## 已实现的边界

- 资源业务、导入、凭据、验证/识别调度、项目反扫、异步批量和 Web 页面由 Proto 独立实现，位于 `internal/proto`、Web 的 `admin-proto` 和 `*proto*` 文件中。
- 下单继续进入原 Trade，分配继续进入原 Alloc。Proto 分配、历史使用、永久失效补偿和 MailMatch 抓信适配分别有独立分支，没有增加第二个商业入口。
- 资源使用 `email_resources.id`；`proto_resources.id` 与根表同主键。订单通过 `order_no → proto_allocations → resource_id` 关联，没有增加 `orders.proto_*` 或订单资源 ID 列。
- 原四类邮箱的业务分支保留。Gmail 服务模式和商品权重的无关改写已恢复；公共模块只补 Proto 分派、查询、配置、统计与接口契约。旧微软共享任务标签仅增加 `bulk_disable` 的展示分支。

## 资源与异步修正

- 所有单项资源写请求携带 `version` 和 `Idempotency-Key`。资源根锁、回执预留、业务变更、安全审计和结果回执处于同一个事务；失败不遗留假成功回执。
- 根→子锁序一致，owner/version 以根为权威。改邮箱清除旧密码，凭据和验证代次失效；禁用阻止新分配，删除仍保护活动订单。
- `for_sale` 表示供货意愿，验证/识别/永久失效不会自动清掉它；可用库存还必须满足健康、归属、供给和协议条件。删除恢复保持私有。
- 导入固定 `邮箱----密码`，保留密码空白、BOM/CRLF 与原始行号。原件和安全失败 CSV 为私有文件；用户只能读取自己的导入和失败制品。
- 导入使用 generation/claim 领取、1000 行短事务、行结果幂等和断点恢复。根和子表不会因吞掉行错误而留下孤立根；批次重试有明确上限，计数保留已提交事实。
- 验证从持久 pending 资源领取；worker 先于 dispatcher 完成时不会被重新改成 validating。验证与识别 TODO 对当前代次形成可观察终态，周期任务不重复运行它们。
- 批量支持 IDs/filter、提交时冻结目标上界、100 条分页、独立 Redis lease、canonical payload、逐项幂等和进度。重复请求与周期 seeder 可续投丢失的队列交接。
- 外部批量任务 ID 为 `proto_bulk:<数字>`，既可用 Proto 进度接口，也可通过公共 TaskView 查询。公开 DTO 不包含协调 token、指纹或内部游标。
- 资源验证后的识别和项目创建/审批/编辑后的反扫分别有入口；后者使用 `proto_project_history_scan_states`，不修改微软扫描进度。
- 背景工作使用现有执行容量控制，dispatcher 不占工作窗口；任务、Redis key 和队列命名保持 Proto 隔离。

## 公共接入和 Web

- 项目/商品、固定主邮箱权重、默认售价/供货价、产品倍率、库存查询、分配查询/释放、订单恢复、历史订单、Token、退款、供应商履约统计和管理仪表盘已接入。
- MailMatch 增加 Proto 的订单/单笔/批量取码作用域、精确收件人匹配、revision 校验、缓存隔离、管理员消息和抓信状态、Bot 诊断及永久失效回调。
- 管理员主动抓信继续使用按全局资源 ID 隔离的公共 `mailmatch_admin_resource_fetch_states`，新增操作类型 `proto_resource_fetch`，没有新造一张重复抓信状态表。
- 新增独立 `/v1/open/proto/resources...` API Key 资源接口。仅允许自有资源管理，单项操作有版本检查，公开批量只允许 validate/delete；原 `/v1/open/resources` 不变。
- Web 的用户页、管理页、导入/编辑/凭据弹窗、维护、批量、详情、关联分配分页均从微软独立复制。保留后缀/日期/状态/facets、分块分页、移动端、供应商门槛、人机验证、请求取消和中英文。
- 详情有基本信息、订单、任务、邮件；邮件 HTML 使用 sandbox。导入失败不会弹成功，查询错误不会伪装成空列表，批量与导入可查询后台进度和下载安全失败明细。
- 主 OpenAPI、Go/TypeScript 生成类型与公开 OpenAPI JSON 已同步。

- 删除管理员通配命令路由，封住 `operate` 权限调用 `edit` 的旁路；PATCH 含密码时额外检查 `operate`，与微软字段权限一致。
- 批量操作的持久幂等身份改用稳定 BatchID，Redis 自增编号仅作为任务查询 ID。Redis 重建后不同客户端 key 的新命令仍会执行；已接受的旧队列 payload 沿用旧回执键，避免在途任务重复执行。

- Proto 候选资格使用微软式 EXISTS 查询，外层只锁 Proto 子表；同供应商不同资源不会因额外锁住 users 行而互相跳过，统一根锁顺序不变。

## 迁移与验证

`00136`、`00137` 保持同样的目标表结构，补齐了可重入的 Up 路径，参考仓库既有 `00077`、`00086` 的写法。不会修改 `00135` 及以前的成熟迁移，也没有新增订单资源列。

`00136` 跳过已经扩展的共享 CHECK，Proto 表使用 `IF NOT EXISTS`；`00137` 在改业务表之前检查冲突回执 key、非法导入行号、孤立资源引用和超长域名，再按实际列/索引/约束逐项继续。不会删除或覆盖冲突记录以强行通过迁移。两个过程均限制元数据/行锁等待为 5 秒，结束或 SQL 错误时恢复原 session 设置。已经成功应用的版本不会因迁移文件更新自动再次执行。

新增服务器参数 `--migrate-only`，执行迁移和必要的版本核验后退出，不启动 HTTP、SMTP、后台消费者或诊断服务器。CI 顺序变为：停止旧 server → 一次性迁移容器执行完毕 → 启动正式 server → 开始约 60 秒就绪检查。部署任务总预算改为 45 分钟，迁移不会再被 HTTP 的 60 秒就绪预算中途终止。

这仍是单实例维护停机发布，不能称作零停机迁移。5 秒限制的是等待锁的时间，并非 CHECK 校验或 DDL 的执行时间；上线前仍需按线上数据量评估维护窗口。回滚镜像不等于回滚已提交的 MySQL DDL，有 Proto 数据时 Down 仍拒绝直接丢弃事实；迁移被中断后优先重跑可重入 Up。
