## 决策与隔离边界

参考脚本的 SRP 登录、会话复用和 PGP 解密流程；底层协议还核对了脚本依赖 `protonmail-api-client` 的 DEV 模式以及 Proton 的 Go API 客户端源码。生产实现不运行 Python，不读写或反序列化 pickle 文件。

HTTP 会话独立复制微软客户端的设计，代码在 `internal/proto/infra/proton`：已有的 `tls-client`/`fhttp`、Chrome 124 指纹、cookie jar、禁用 HTTP/3、正常 TLS 校验、禁止跟随重定向、30 秒请求超时和 context 取消。Proto 使用独立的 `proto:<全局资源ID>` 代理绑定，通过原公共代理入口取代理；不引用或改写微软的客户端、私有表及任务。

选择原生 Go，而非 Python 子进程或引入整套 Proton Bridge 客户端：复用仓库已有 HTTP 栈，仅增加必要的 Proton SRP/PGP 密码学库及其依赖。SRP、签名验证和 PGP 不自行实现。库版本锁定于 `go.mod`；没有升级现有依赖的版本。

下单、分配、订单、钱包、取码和消息存储仍使用原统一入口。Proto 的边界适配在 `api/proto_resource_adapter.go`，订单表没有新增资源关联列。

## 验证和密钥持久化

导入格式保持 `邮箱----密码`，不裁剪密码。验证任务执行：

1. 短事务按根资源→Proto 资源领取维护任务，记录本次 attempt，校验归属、凭据 revision 和 validation generation。
2. 退出事务后，调用 `/auth/v4/info` 与 `/auth/v4` 完成 SRP。验证签名 modulus 和服务器 proof，不把拿到 Token 当成充分的验证成功。
3. 按 Key ID 读取邮箱盐，解锁用户私钥；解密地址 Token 并验证其签名，再解锁地址私钥。导入地址必须属于该账户的有效收件地址且有可用密钥。
4. 再次检查任务归属，原子保存密文会话、将资源设为 `identifying`、创建历史识别任务。登录期间改密码、改邮箱、转移归属、禁用或删除，会使旧任务不能提交。

新表 `proto_sessions` 以全局资源 ID 为主键，保存 `credential_revision`、会话 version、加密 payload、lease token/期限及时间戳。payload 包含 UID、access/refresh token 和已解锁的用户/地址私钥；不会进入资源 DTO、公开接口、队列 payload 或日志。

加密使用 AES-GCM 随机 nonce，AAD 绑定资源 ID 与凭据 revision。使用现有 `SESSION_SECRET` 经 HKDF、独立用途 `remail/proto/session/v1` 派生密钥，不复用其他模块的加密实现。代价是更换 `SESSION_SECRET` 后旧 Proto 会话无法解密：读取时会停止使用旧会话并请求重新验证，也可以主动批量验证。旧邮箱模块的凭据不受此机制影响。

## 复用密钥收件

普通收件、管理员抓信和历史识别统一调用 Proto 自己的 `Service.FetchMailbox`。这个入口不重新进行密码登录，只读取持久化密钥、复用或刷新会话。

- 普通收件和完整历史扫描读取各自的会话快照，不领取整段独占租约；后台扫描不会因此阻塞实时收件。完整读取仍最多 15 分钟。
- DB lease 只覆盖刷新令牌交换及持久化，刷新操作最多 60 秒、lease 为 90 秒；验证和历史维护任务的 15 分钟操作上限/16 分钟防重复领取期限保持不变。网络调用不持 SQL 事务，数据库读写均为短事务。
- 刷新开始时在租约内重新加载最新会话：其他 worker 已完成相同会话的有效 Token 轮换时直接复用，不再次消费旧 refresh token。新 Token 必须先保存并完成 revision/version/lease 检查，才返回给 HTTP 客户端继续请求。
- 完整读取结束时再次检查凭据 revision 和可用会话。正常 Token 轮换不会作废已解密的读取结果；新登录 UID 或用户/地址密钥集合变化则要求旧读取者重新加载密钥，不用旧 key ring 读取新会话。
- 正常/识别中的资源缺少密钥、密文无法解密或会话被撤销时，转入验证恢复；修复检查最初观察到的 generation 和 refresh token，迟到请求不能删除其他 worker 刚保存的新会话。已停在 pending/uncertain 等待人工处理的资源仍需显式重验，不会绕过其终态自动重复登录。
- 读取 Inbox `0` 和 Spam `4`，分页取得邮件详情并解密正文。脚本使用的 Label `5` 实际是 All Mail，不是收件箱；本实现按微软现有机制扫描收件箱与垃圾箱，不宣称包含归档、已删除、已发或草稿。
- 普通取码支持时间窗口、数量限制和公共消息缓存的 `internet:` / `provider:proton:` 边界。先按导入地址精确筛选，不将同 AddressID 下的 dot/plus 或其他显式收件地址推断成当前资源。
- 完整历史扫描不受取码数量和已有缓存边界截断；通过逐页回调汇总证据。任何分页、解密、持久化或回调失败都不能产生完整成功结果。
- MIME 正文排除附件和嵌套附件；没有实现附件下载。公开消息仍走既有取码规则和管理员 HTML sandbox。
- 邮件详情必须包含加密 Body；缺字段/null、坏密文或无法解析的正文不能被当成完整空邮件。合法空正文必须由有效密文解密得到；无附件标记的 inline `message/rfc822` 递归解析，深度和大小上限继续生效。

## 旧项目识别

独立复制微软项目范围、规则匹配、事务提交和项目反扫机制：

- 验证完成后扫描当前所有 Proto 项目。包含已下架项目及仍存在的 Proto 商品，以保留历史使用约束。
- 历史证据要求原始 To 数量恰好为 1，且主邮箱精确匹配；不推断 CC/BCC、dot/plus。
- 严格模式匹配 recipient、sender、subject、body；宽松模式匹配 recipient 和 sender。不要求一定提取出验证码。
- 历史和实时收件使用同一个 Proto sender 格式：无显示名时是裸邮箱，有显示名时是 `Name <address>`，锚定正则不会因两条路径格式不同而出现矛盾。
- 完整扫描成功后，短事务重新检查资源 owner/generation/revision 及项目规则快照，再调用原 Trade 的 `ImportHistoricalProtoUsage` 写入历史订单、分配与零额账务事实，最后将资源设为 `normal`。部分扫描不提交部分历史结论，也不直接放入可用库存。
- 项目新增/修改后的反扫冻结 `ThroughID`，一任务处理一个资源，持久化 `AfterID`。历史事实和游标提交后续投，入队丢失可由 dispatcher 接续；旧 payload 不会重复计数。
- 管理端批量商品 upsert 成功后，请求中含 Proto 才按相同筛选条件读取实际受影响项目并调度。重复、已删除、不存在、未选中项目不会多建任务；disabled Proto 商品也保留历史扫描。微软/Gmail/域名商品的批量行为与共享 Repository 签名不变。
- 活跃任务不可重复领取；过期 worker 的成功和失败均受本次 attempt 检查，不能覆盖新任务。项目扫描遇无法解密、协议不兼容或人工验证要求时保留明确的未完成状态，不推进游标假装成功。

## 错误、库存和订单安全

仅明确的账户凭据错误或账户身份不符进入 `abnormal` 和原永久失效补偿流程。需要人工操作、协议不兼容、解钥异常、暂时网络故障和限流耗尽不直接进入永久退款扫描：资源保持 `pending`，维护任务为 `uncertain`，或在预算内进入新代次重试。会话撤销先尝试验证恢复，不直接退款全部活动订单。

HTTP 响应必须先通过 Code/envelope 校验，缺失地址列表属于协议错误；无法解析的 401 HTML 或未知登录 401 不推断成密码错误。地址接口按现有官方参考单次读取完整数组，不按 150 条猜测分页；150 条以上及 disabled 地址不会引发虚假的重复页失败。

重新验证遇到非永久错误时，保留同一凭据版本此前已验证的会话，供已有订单继续使用；资源仍为 pending，不能新增分配。只有明确的永久凭据失败才删除这份会话，密码/邮箱/归属变更和删除资源的原清理规则不变，避免临时异常间接中断所有在服订单。

装配真实客户端后开启 Proto 协议入口；公有/自有库存、候选和锁后重查、仪表盘可用量均要求存在与当前 credential revision 相同的密钥记录。仅手动把资源状态设为 normal 不能变成可分配库存。

已存在的分配在复用、`paid` 订单激活和签发 Token 前也检查当前会话，不能绕过候选条件。协议已装配但该资源不可用时，只对当前未交付的已付款订单调用原单笔补偿逻辑、退回原款并释放分配，避免永久停在 paid；数据库查询失败不伪装成库存不足并退款。全局协议未装配时保留暂停恢复规则；其他邮箱类型和已 active/completed 的订单幂等读取不变。
