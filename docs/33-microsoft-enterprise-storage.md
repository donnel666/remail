# 微软企邮独立存储

状态：已实现，待部署。日期：2026-10-20。

## 问题和决定

企邮与个人邮箱是两个独立商品。旧实现把两者放在 `microsoft_resources`，通过 `email_domain LIKE '%.onmicrosoft.com'` 区分。线上企邮只有 20 条，个人邮箱表约 640 万条；慢日志中企邮列表 SQL 耗时 16.375 秒，用户分类统计的两条 SQL 分别耗时 12.954 秒和 11.309 秒。筛选条件无法提供物理隔离，继续在个人邮箱大表上加索引也不符合商品独立的要求。

企邮使用独立类型 `microsoft_enterprise` 和四张表：

- `microsoft_enterprise_resources`：凭据、状态、验证代次、RT 刷新状态及库存分桶。
- `microsoft_enterprise_allocations`：只允许主邮箱分配，不允许显式、点号、加号别名。
- `microsoft_enterprise_project_matches`：原有项目识别记录；后续历史识别的订单及分配也使用企邮类型。
- `microsoft_enterprise_history_scans`：企邮项目级历史扫描的独立状态、代次和进度。

用户和管理员企邮页面的列表、数量、分类统计、搜索均查企邮表，分类缓存的键和失效版本均区分商品类型。验证和历史识别继续使用既有的企邮专用队列；企邮 RT 刷新也进入企邮验证队列，调度额度按产品分别读取。导入和管理员拉信使用独立的 `microsoft_enterprise` 前台队列；派发任务的载荷指定商品，每次只读取该商品。项目扫描与验证后历史识别使用独立的并发计数及配置。RT 定时到期扫描有独立的计时器和扫描配置，退款扫描也有独立查询及额度。

平台的资源 ID/归属表 `email_resources`、订单、钱包、导入记录和任务元数据仍是所有商品共用的基础设施。微软 OAuth/Graph 协议代码和安全 DTO 可以复用；资源、分配、历史记录及 RT 状态的读写必须按实际资源类型选表。普通用户的资源查询与修改保留归属检查，订单与邮件读取保留买家或服务令牌校验。

## 迁移和部署边界

`00154_microsoft_enterprise_storage.sql` 新建企邮表并以 `ALGORITHM=INSTANT` 扩展公共表的类型白名单，沿用现有迁移中不强制执行白名单 CHECK 的方式。它不会 ALTER 或重建个人邮箱资源表，也不会修改个人邮箱记录。

搬迁先对旧表的后缀覆盖索引扫描一次，收集遗留企邮 ID；这一遍扫描仍随旧表规模增长，不能承诺迁移立即完成。之后只对这些 ID 执行事务：锁住资源根记录，暂存企邮凭据及项目历史，将其搬入企邮表并修改根类型，保留 ID、归属、凭据版本及时间。旧验证、历史识别、RT 刷新和管理员拉信任务增加代次，进行中的任务回到待调度状态，旧 worker 的结果不能覆盖新状态。锁等待上限为 5 秒，冲突会失败退出，不长时间等待。

2026-10-20 通过 SSH 只读复核：遗留企邮 20 条，关联分配、邮件、显式别名和绑定邮箱均为 0。迁移遇到既有分配、任意别名、绑定或邮件依赖会拒绝搬迁并回滚数据事务；已创建的空表可以在重试时复用。不得通过关闭外键或删除业务依赖强行迁移。

部署时需停止旧版本 worker 和写入后再运行迁移并启动新版本，避免旧代码继续写入个人邮箱表。迁移完成后不能直接回退到只认识共享表的旧应用；Down 明确拒绝删除企邮业务数据。代码尚未部署，本次工作没有修改线上数据库。

## 验证重点

回归覆盖用户/管理员列表和分类缓存的双向访问顺序、归属隔离、企邮查询不引用个人邮箱表、迁移保留数据及失败回滚/重跑、验证队列隔离、库存与分配保护、下单幂等、接码及服务令牌隔离、退款释放和供应商统计、企邮 RT 刷新与个人邮箱状态隔离。外部微软收件和 OAuth 换取 RT 的真实网络行为不属于这些使用合成数据的回归测试。
