# 苹果设备码接入

系统设置 → 上游设置 → 苹果设备码配置管理 API Key、公网短信回调地址和设备平台地址。UID 固定为 919。旧资源按是否已有 `device_code_api` 选择取码方式：没有 API 时继续短信，有 API 时使用设备码；仅配置全局 API Key 或存在绑定状态不会强制迁移旧资源。新开户在配置 Key 后主动初始化设备绑定并等待成功；保存设备 API 后，后续验证不自动回退短信。命令行已完成第一阶段的旧检查点同样保留原有短信模式。

手机验证完成后保存绑定意图，最早 30 秒后导入设备平台。共享 Asynq 任务通过有时限的去重机制批量检查待绑定账号，Redis 将运行频率限制为每 10 秒一次。命令行验证器和 Web 工作流使用同一个持久化绑定队列；命令行运行时需要服务端 Asynq worker 在线。

`icloud_device_bindings` 保存尚未建成邮箱资源的命令行账号和 Web 账号的绑定状态。密码和短信回调凭证仅在绑定期间保留，绑定完成或失败即清除。邮箱资源保存 `device_code_api`、`device_bind_status`、`device_account_id`，Cookie 更新不会清空它们。列表只返回状态及可用标记，完整设备 API 经有短信查看与资源操作权限的管理接口获取。

设备绑定成功且有可用 API 后，阶段 2、阶段 3及后续 Cookie 恢复统一使用设备码。阶段间随机等待为 1～30 秒。设备码通过 Apple 的 `/auth/verify/trusteddevice/securitycode` 提交，不调用短信派发接口。

## 余额与充值

设置页通过 `GET /api/auth/me` 读取 `data.balance`，展示剩余 tai 点及查询时间。余额为 0 时正常显示；未配置 Key 时显示未配置，不伪装成 0。

卡密兑换调用 `POST /api/balance/recharge/card`，请求体为 `{"card_key":"卡密"}`。参数名由平台公开前端确认；充值响应按提供的 `code=0`、`data.balance` 更新余额。充值需要系统设置写入及敏感权限，使用 CSRF 和调用频率限制。卡密不入库、不写日志；充值请求不自动重试，结果不确定时先刷新余额核对。
